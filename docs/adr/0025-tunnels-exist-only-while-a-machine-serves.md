# Tunnels Exist Only While a Machine Serves

A machine's Cloudflare tunnel is created when the machine first has to carry traffic, and deleted when it stops: it no longer serves any URL, its owner loses the entitlement, or Cloudflare has seen it down for 15 minutes. This amends ADR 0019, which kept one tunnel per signed-in machine, and ADR 0020, whose sign-in created that tunnel. Signing in now makes no Cloudflare call. The reason is cost: Cloudflare counts every tunnel that exists, connected or not, and charges $4.50 a month for each one past 1,000. A laptop that is asleep or closed then holds no tunnel. What we pay follows the machines serving at the same moment, not the accounts. T3 Connect, which runs the same design, reclaims idle tunnels the same way.

The machine's hostname `m-<machine-id>.localify.dev` and its CNAME outlive its tunnels. A new tunnel only moves the CNAME's target, so no DNS name is created or removed on every wake-up. Each tunnel belongs to one **generation** of its machine, a counter that every provisioning bumps, and it is named `localify-<machine-id>-<generation>` so a retry finds it by name. Generations start at 1: 0 only means "no tunnel, no token", and the tunnels created before this decision become generation 1. A provisioning or a release holds the machine row through an operation id. Every write it makes is conditioned on that id and that generation, so a stalled operation can neither overwrite a newer one nor delete its tunnel. A generation check cannot stop a DNS call already on its way. The scheduled check therefore compares each CNAME with its machine's current tunnel and corrects it.

A **serving slot** is a machine holding a tunnel in any state but none: provisioning, ready, or releasing, since a tunnel still being deleted still counts at Cloudflare. A slot is reserved in the same statement that starts the provisioning. That statement checks both the owner's serving-machine limit and the account-wide cap `MAX_TUNNELS`, set to 950, so concurrent requests can never pass either one. An alert fires at 800. The cap leaves room for tunnels still being deleted and for growth until more are bought. When the cap is reached, the machine waits in a `capacity` state instead of failing silently.

A reap needs proof. It requires two status readings at least 15 minutes apart that both say down, and a tunnel that became ready more than 15 minutes ago. A status reading that fails counts as no reading, not as down. A sweep works within a budget of Cloudflare calls and starts with the machines seen down the longest, so a backlog drains over several runs and never exhausts the account-wide API limit. The daemon gets a tunnel token only when its generation changes, which spares a Cloudflare call on every runtime poll. The `/v1` runtime that installed clients still call runs the same reservation and provisioning, and returns the current token whenever the tunnel is ready. Turning anyone away (`blocked`, `402`) waits for the daemon release that understands it.

A machine hostname is public, and a tenant holds the tunnel token their daemon runs. With it, they could run their own origin and serve any page on `localify.dev` straight to a victim, past the Worker and the warning page. The `localify.dev` zone closes that. A WAF custom rule blocks every request to `m-*.localify.dev` that does not carry the `EDGE_KEY` secret in `X-Localify-Edge`, which only the Worker sends. A late request-header transform rule then removes the header before the request reaches the tunnel. A tenant who learns the key gains nothing, because a victim's browser never sends it. After a sleep, or when `cloudflared` keeps failing, it fetches its runtime again right away, with jitter.
