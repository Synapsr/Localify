# Localify Cloud Is Paid and Billed Through Polar

Public URLs are a paid feature with no free tier. Pro costs $7.99 a month or $79 a year, or €7.99 and €79 in euros, and starts with a 7-day trial that asks for a card up front. It includes 2 serving machines and 10 public URLs. Add-ons, which ship after launch, are separate monthly subscriptions that need an entitled Pro plan: one more serving machine for $3, ten more URLs for $2. Signing in with GitHub stays free and gives an account, but without a plan no machine can create, claim or serve a public URL. The Team plan shows up on the pricing page only as "contact us".

The plan keeps the costs and the abuse in check. Each serving machine holds a Cloudflare tunnel, and past the 1,000 tunnels an account includes, each one costs $4.50 a month. A card and a GitHub account behind every URL make throwaway accounts expensive and leave someone to answer for each one.

Polar is the merchant of record, so it collects VAT and sales tax worldwide and Localify only receives payouts. Its fees, about 4% plus $0.40, cost more than Stripe's, but nobody has to file VAT returns in every country. Each product has a USD and an EUR price, and Polar picks the currency from the IP address that creates the checkout. The Worker creates it, so it passes the buyer's address from `CF-Connecting-IP` as `customer_ip_address`; without it, every buyer would see the currency of a Cloudflare address. Polar knows each customer by an external id, which is always the Localify user id. A client never chooses it. The Worker keeps a snapshot of each user's subscriptions in D1 and never calls Polar on the public path. Webhooks are verified on the raw body, recorded under their `webhook-id`, and only tell the Worker to refresh that user from Polar's subscription list. Every refresh takes the next value of a per-user revision counter in D1. Its snapshot, and the work that follows it, commit only while that revision is the latest. A snapshot that changes leaves a serving reconcile owed, recorded in the same commit and cleared only by the reconcile that commits; every write of that reconcile holds only while the snapshot is still the one it read, so an overtaken refresh cannot suspend a plan a newer one restored. Before fetching, the refresh notes the highest event it has stored. Once its work has committed, it marks as processed only the events at or below that point. A failed refresh leaves its events pending for a retry, and an event that arrives during a refresh causes another one. Webhook delivery is therefore never the source of truth: a delivery that arrives late, twice or out of order changes nothing. Once a day, every customer with a snapshot, a checkout or a Polar subscription is checked again, so a delivery that never came costs at most a day. The redirect after checkout grants nothing. Every call pins `Polar-Version: 2026-10`, and the webhook endpoint pins the same `api_version`, so a quarterly Polar release changes nothing until we move.

An **entitlement** is what an account may use: serving machines and public URLs. It comes from the plan's state (the lifecycle table in `docs/public-urls.md`) plus the add-ons, or from an **override**. An override is a row with explicit limits, a reason and an optional expiry, and it replaces what the plan gives. The people on the old allowlist get one through a single migration that runs once, so they keep their access without paying. A **ban** beats every grant. Banning someone refuses their API calls, takes their URLs offline and releases their tunnels.

Who may sign in and who may serve are two separate switches. `SIGNUP` is `allowlist` or `open`, and it only decides whether a GitHub account may finish a new sign-in. Entitlements are always enforced, in both modes. Moving back to `allowlist` blocks new sign-ins and leaves existing accounts and their plans alone. Paying customers therefore never lose access when sign-up closes again.

Trials are tracked against the GitHub identity as well as Polar's email and card checks. The refresh looks for a `trial_start` on every Pro subscription the user ever had. Once one is found, every later checkout for that user is created without a trial. A user has at most one pending Pro checkout, covering both intervals, and creating it is serialized. A user who already has Pro gets the customer portal, where the interval is switched, never a second checkout. If two Pro subscriptions exist anyway, the refresh keeps the one it already kept while that one is entitled, otherwise the one ending latest, revokes the other through the API, and raises an alert. The commit refuses a snapshot that keeps a subscription already recorded as a duplicate, or records the one already kept, so two refreshes that cross never revoke both. An operator refunds the duplicate in Polar's dashboard, from a read-only listing of its orders taken live from Polar. Refunds are not automated: with one pending checkout per user and the portal for anyone who has Pro, a duplicate should all but never happen, and an automatic refund would bring its own lifecycle (pending, failed, reversed, payments that complete after the revocation) onto the path that moves money, for a case a person handles in minutes. A `past_due` plan stays entitled for 7 days from Polar's `past_due_at`, while Polar retries the card.

## Addendum: add-ons when Pro lapses

Add-ons are cancelled at period end when Pro lapses; they are not resumed automatically if Pro comes back. Pro has lapsed when it is not entitled and not `past_due`. The 5-minute job cancels each add-on that still renews, through Polar's API and without a refund, after checking the user's current snapshot in D1 right before the call. The Worker never sets an add-on to renew again: like a refund, that is left to the person, who resumes the add-on in the customer portal or buys it again. That also leaves alone an add-on the person canceled in the portal themselves.
