# Remote Controls Respect Service Ownership

A paired machine may start, stop and restart a service on a target that allows it, and every control goes through whoever owns the service there. This amends ADR 0012 a second time, after ADR 0030 made a service tab the run itself. PTY ownership stays in the desktop app, the only thing that creates terminals. A service tab no longer holds a shell, so the app no longer writes a command into a tab to start a service, nor Ctrl-C to stop it. Stop and restart signal the run's own session and process group, each process checked against its start time, and a Ctrl-C written to a tab could have reached an editor or a REPL instead. The app also accepts launches from the daemon over a narrow local bridge. The deep link that `localify dev --in-app` uses has no acknowledgement, which is not enough to tell a start that happened from one that did not.

The bridge is a Unix socket that only its owner can open, served by the app while it runs, with one request per connection: `hello`, and `launch`, acknowledged once the app has spawned a fresh run PTY. The routing follows the owner:

- **App running on the target:** a start goes through the bridge, and the service opens in a new tab of the app's terminal panel, as its launch button would open it.
- **App absent:** a start runs detached in the background, and only when the target has turned on "allow background starts when the app is closed". That is a third switch, separate from sharing and from control, all three off by default.
- **App disappearing mid-dispatch:** the target reconciles. It waits until the launch's expiry has passed, after which that launch can no longer start, and answers from what exists: the run, a refusal, or nothing. It never falls back to a background start for a launch it handed to the app, which could start the service twice.
- **An app or background run:** stop signals the run's session and process group, and the run is over once nothing of it is left. Restart stops it, then launches it again through the same owner on the run's profile. Every reason to refuse the replacement is decided before anything stops: a profile no longer permitted, an owner that is gone, or a background replacement without background starts allowed.
- **A run in the user's own terminal, or an unknown listener on the port:** the target shows what it observes and refuses the control in v1. Taking over a process someone else holds is not a remote decision.

The process that executes the run, `localify dev` itself, is the only owner of the service's lock. In a person's terminal, in a run PTY or detached, it takes an exclusive `flock` before running anything and holds it until it exits, so the OS releases it even after a crash. It registers the run atomically under that lock, and a failure to register is fatal. Dispatchers (the daemon, the bridge, the app's own button) never hold the lock. They pass a launch id, which becomes the run id, and an expiry 15 seconds out. The executor refuses when the lock is held or the expiry has passed, so a launch that arrives after its dispatcher gave up starts nothing. It also recomputes the service's revision and refuses on any change since the target's check, then runs from the definition it checked, never a second read. The revision is an HMAC under a per-machine secret over the config entry and the full launch-profile definitions, inline overrides included, so a revision reveals nothing about a low-entropy value. Profiles follow the same effective rules as a local launch: the implicit Infisical `default` and `staging` are allowed, and a dangerous profile, the implicit `prod` included, is refused. Under the remote-launch context, which only the daemon and the bridge set, that refusal holds even inside a PTY. The context only adds restrictions, so it needs no authentication.

Each launch has one durable record, created with `O_EXCL`, exactly once, by whichever side decides first: the executor admitting or refusing the launch before it runs anything, or the reconciler declaring it expired once its expiry has passed. The loser obeys the file, so a launch delayed between its checks and its admission cannot start after its dispatcher gave up. An admitted launch keeps its record, apart from the service's current record, and gets its exit added when the run ends. A target therefore reports exactly what happened to a launch whose acknowledgement was lost: running, exited with its code, replaced, refused, or expired without starting. A viewer that lost its session asks for that report by request id, instead of resending the control.

Controls name explicit ids: machine, project, environment and service, plus a profile name for a start. Each carries the run and the revision the viewer saw, and an expiry in the target's clock, and the target runs one control per service at a time. A request id is correlation, not exactly-once: a lost acknowledgement means "outcome unknown" until the launch record answers, a restart repeated under the same request id gets the recorded report, and one repeated under a new request id fails because the run it expected is gone. A control never carries a command, a path, an env file or value, an option that creates a project, or a dangerous launch profile. The target checks its own settings and a fresh authorization lease before each one.
