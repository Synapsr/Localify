# Remote Controls Respect Service Ownership

A paired machine may start, stop and restart a service on a target that allows it, and every control goes through whoever owns the service there. This amends ADR 0012 a second time, after ADR 0030 made a service tab the run itself. PTY ownership stays in the desktop app, the only thing that creates terminals. A service tab no longer holds a shell, so the app no longer writes a command into a tab to start a service, nor Ctrl-C to stop it. Stop and restart signal the run's own process group, validated by its PID and start time, and a Ctrl-C written to a tab could have reached an editor or a REPL instead. The app also accepts launches from the daemon over a narrow local bridge. The deep link that `localify dev --in-app` uses has no acknowledgement, which is not enough to tell a start that happened from one that did not.

The bridge is a Unix socket that only its owner can open, served by the app while it runs, with one request per connection: `hello`, and `launch`, acknowledged once the app has spawned a fresh run PTY. The routing follows the owner:

- **App running on the target:** a start goes through the bridge, and the service opens in a new tab of the app's terminal panel, as its launch button would open it.
- **App absent:** a start runs detached in the background, and only when the target has turned on "allow background starts when the app is closed". That is a third switch, separate from sharing and from control, all three off by default.
- **App disappearing mid-dispatch:** the target reconciles. It waits until the launch's expiry has passed, after which that launch can no longer start, and answers from what exists: the run, a refusal, or nothing. It never falls back to a background start for a launch it handed to the app, which could start the service twice.
- **An app or background run:** stop signals the run's process group. Restart stops it, then launches it again through the same owner on the run's profile. Every reason to refuse the replacement is decided before anything stops: a profile no longer permitted, an owner that is gone, or a background replacement without background starts allowed.
- **A run in the user's own terminal, or an unknown listener on the port:** the target shows what it observes and refuses the control in v1. Taking over a process someone else holds is not a remote decision.

The process that executes the run, `localify dev` itself, is the only owner of the service's lock. In a person's terminal, in a run PTY or detached, it takes an exclusive `flock` before running anything and holds it until it exits, so the OS releases it even after a crash. It registers the run atomically under that lock, and a failure to register is fatal. Dispatchers (the daemon, the bridge, the app's own button) never hold the lock. They pass a launch id, which becomes the run id, and an expiry 15 seconds out. The executor refuses when the lock is held or the expiry has passed, so a launch that arrives after its dispatcher gave up starts nothing. It also recomputes the service's revision, which covers its config entry and the launch-profile definitions, and refuses on any change since the target's check. Under the remote-launch context, which only the daemon and the bridge set, it refuses a dangerous profile even inside a PTY. That context only adds restrictions, so it needs no authentication.

Controls name explicit ids: machine, project, environment and service, plus a profile name for a start. Each carries the run and the revision the viewer saw, and an expiry in the target's clock, and the target runs one control per service at a time. A request id is correlation, not exactly-once: a lost acknowledgement means "outcome unknown", followed by a fresh snapshot, and a restart repeated after a reconnect fails because the run it expected is gone. A control never carries a command, a path, an env file or value, an option that creates a project, or a dangerous launch profile. The target checks its own settings and a fresh authorization lease before each one.
