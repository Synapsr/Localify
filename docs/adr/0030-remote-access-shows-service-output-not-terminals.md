# Remote Access Shows Service Output, Not Terminals

Version 1 of remote access shows a service's output, read-only, and never a terminal. There is no typing, no PTY attach and no resize. The panel is labelled "Output" and shows plain, sanitized lines with selectable text, search, and follow or pause. xterm.js may render it read-only, but it receives the same plain lines, never raw bytes. Typing into another machine's shell is remote code execution with extra steps. It would need its own permission model, its own audit and a terminal protocol over the relay, for a need that output and start, stop and restart already cover.

Output must be the service's own, for one run. Today an app-owned service tab copies every byte of its shell into the service's output file, prompt and later commands included, so a command typed after the service exits would be exported. That file is never sent anywhere. Instead, each run gets a run id and a per-run stream in segments under the state directory. A background run's stream is its stdout and stderr, read through pipes. For an app run, `localify dev` marks the start and the end of its run in the terminal with an OSC sequence that xterm.js ignores. The app writes the PTY's bytes to the stream only between those markers, and only while the run's process leads the terminal's foreground process group. Neither writer takes a path from the output. Until a target's app and CLI both support this, its app runs report their output as unavailable, never the old file. `localify logs` moves to the same stream, so agents stop reading shell prompts too, and the whole-shell copy goes away.

This was chosen over reporting app output as unavailable for good, because most services run in the app, and over a nested PTY in `localify dev`, which would make it a terminal multiplexer forwarding resizes, signals and raw input. The cost is that keystrokes echoed while a service runs in the foreground stay in its stream, as they would in any terminal log.

Reads take a run id and an offset, read a bounded number of bytes from the segment at that offset, and never read a file to its end. Offsets are logical and never reused across rotation. A read below what is kept says the output was rotated, a run id that is no longer current says the service restarted, and a line longer than 8 KiB arrives in bounded pieces. A follow is flow-controlled by the viewer's acknowledgements, expires without renewal, and ends when the panel closes, so no output streams when nobody reads it.
